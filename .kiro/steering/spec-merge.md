# 個別 Spec のメイン Spec への統合ルール

個別 Spec（機能追加・バグ修正などの目的で `.kiro/specs/<name>/` に作成された Spec）を
メイン Spec（プロジェクト全体の仕様を定義する Spec）に統合する際のルール。
統合後のドキュメントは、初めて読む者にとって自然で、無駄や抜けがない状態を目指す。

## 基本原則

- **現在形で記述する**: 統合後のドキュメントは「今のシステムの仕様」を記述する。変更履歴や修正過程は含めない。
- **初見で理解できる**: プロジェクトの変更経緯を知らない読者が、ドキュメントだけで全体像を把握できること。
- **重複を排除する**: 同一の仕様が複数箇所に記述されないこと。矛盾が生じる余地を作らない。
- **個別 Spec は削除する**: 統合完了後、個別 Spec のディレクトリ（`.kiro/specs/<name>/`）を削除する。経緯は Git 履歴で追う。

## requirements.md の統合

### 統合手順

1. 個別 Spec の各 Requirement を、読み手にとって自然な位置に配置し、通し番号を振り直す
2. Introduction を更新し、追加された機能・能力を反映する
3. Glossary に新規用語を追加する（重複は除く）
4. 既存 Requirement の説明が古くなっている場合は現在の仕様に合わせて更新する
5. 番号を変更した場合、design.md の Correctness Properties の `Validates: Requirements` 参照、および tasks.md の各タスクに記載された `Requirements` 参照を更新する

### 禁止事項

- 「〜を追加した」「〜に対応した」等の変更経緯を匂わせる記述
- 統合後のメイン Spec 内で、同一の仕様が複数の Requirement に重複して記述されること（1 箇所に統合する）

## design.md の統合

### 統合手順

1. Overview を更新し、追加されたコンポーネントやアーキテクチャを含める
2. Architecture 図（Mermaid）を現在の全体構成に更新する
3. Components and Interfaces に新コンポーネントを追加する
4. 個別 Spec で変更されたコンポーネントの記述を現在の設計に合わせて修正する
5. Data Models、Error Handling、Correctness Properties を追加・更新する
6. Testing Strategy に新テストファイル・方針を追加する

### 禁止事項

- 「リファクタリングにより〜」「〜から継承に変更」等の修正歴表現
- 個別 Spec の設計がメインの設計と矛盾する記述を残すこと

## tasks.md の統合

### 統合手順

1. 個別 Spec のタスクを、読み手にとって自然な位置に配置し、通し番号を振り直す（全て [x] 完了済み）
2. 既存タスクの説明が現在の設計と矛盾する場合は修正する
3. Task Dependency Graph を全タスクを含む形に更新する
4. `tasks.meta.json` を更新し、番号・タスク名の変更を反映する

### タスク記述のルール

個別 Spec のタスクは差分作業（「〜を変更する」「〜から移動する」等）として記述されていることが多い。
統合時には、これを成果物ベースの記述に書き直す。

**原則:** そのタスクの説明だけを読んで「何を作ればよいか」が分かり、以前の実装を知らなくても違和感がないこと。

**例:**
- 個別 Spec: 「`detect()` の戻り値を tuple から DetectionResult に変更する」
- 統合後: 「`detect()` は DetectionResult を返すように実装する」

### 重複タスクの扱い

統合により既存タスクと同じ成果物を指すタスクが生じた場合:
- 既存タスクの説明を現在の設計に合わせて更新する
- 個別 Spec 側の重複タスクは削除する（追加しない）

## チェックリスト

統合完了時に確認すべき項目:

- [ ] Introduction が現在のシステム全体を正確に要約している
- [ ] Glossary に新規用語が漏れなく追加されている
- [ ] 全 Requirement の Acceptance Criteria が現在の仕様と一致している
- [ ] Correctness Properties の `Validates` 参照が振り直し後の Requirement 番号と一致している
- [ ] tasks.md の各タスクの `Requirements` 参照が振り直し後の番号と一致している
- [ ] Design の Architecture 図が現在の全コンポーネントを含んでいる
- [ ] 既存コンポーネントの説明が現在の実装と整合している
- [ ] 全タスクが「初見で実装可能」な記述になっている
- [ ] Task Dependency Graph が全タスクを含んでいる
- [ ] `tasks.meta.json` のキーが tasks.md のタスク名と一致している
- [ ] 個別 Spec のディレクトリが削除されている
- [ ] 時系列依存表現（language.md の禁止ルール）に違反していない
